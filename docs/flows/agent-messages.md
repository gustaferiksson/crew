# Bot-to-bot messages

A bot (the sender) calls `message_agent`; the other bot (the target) answers in its own Bot Chat; a delivery process carries the reply back to the sender. Hermes stores each step as ordinary rows, so Crew reads the shape from the rows (`Transcript.visible`).

A message another bot sent this bot is a collapsed "Message from <sender>" row. A message this bot sent another bot is not a row of its own: it is the `message_agent` tool row inside the turn that sent it, shown as "Message to <target>" (see Outgoing messages), so it appears where it happened, before the reply that mentions it (user request 2026-11-27, supersedes the standalone "Message to" rows of 2026-11-10). In the sender's chat a paired answer stays a relay line.

Consecutive "Message from" rows with no user-visible turn between them (a bubble, a reply to the user, a notice, a card, or a row that failed) fold into one group row in the same work-log header style (user request 2026-11-27): the participants' 16 pt avatars, "5 messages with Emil" (names joined with "and", count pluralised by the system), a chevron. Expanded, it lists the individual rows unchanged, each still expandable. A single row is never a group. The group pulses while any member runs. Its id is the first member's id plus `-group`, kept in the transcript's turn expansion set; a search hit inside a member expands the group and the member and centres the group. Grouping is a view concern (`Transcript.rows`): the visible turns, preview, time and unread rules are unchanged.

## Target's chat (the bot that was messaged)

- Each exchange started by another bot is one collapsed row in the work-log style: the sender's 16 pt avatar (only when the handle is in the bot list; a relayed or deleted bot shows just the name), "Message from <sender>" with the name from the message itself, a chevron. Like Messages' grouped system rows, it says something happened without competing with the user's own conversation. It is a plain button labelled by its text, like the work-log header, so VoiceOver, Dynamic Type (it wraps) and the Mac keyboard behave the same.
- Expanded, it lists the incoming message, the bot's thinking and tool rows (the `message_agent` reply call included) and any earlier replies, all as secondary work-log note and tool rows, the incoming message first as a quote. The later delivery follow-up turn (the `[IMPORTANT: Background process …` row and the bot's acknowledgement) folds into the same row, so one exchange is one row. It lands seconds after the exchange; if the user has written in between, the follow-up still folds into the row above, which is the honest place for it.
- The exchange's last reply (the final text of the exchange turn itself) is the row's last note, after the incoming message and the bot's work, shown only when the row is expanded (user request 2026-11-27: nothing the bots say to each other shows outside its row; supersedes #285). Nothing in the rows says whom a reply addresses, so a question for the user (recorded in `bot-thread` row 1081: "Do you approve adding a paged reader?") stays in the row too; Crew does not guess from the text. Everything addressed to the user stays outside rows: the user's turns, replies in user-started and routine turns, and the relay reply in the sender's chat. Hermes' silence sentinels (`[SILENT]`, the cron quiet marker; `NO_REPLY`; `(empty)`) never show, as a reply or as a note, in any turn; a turn that was only one disappears. An exchange that ends on a tool call (a reply call and no text, `stale-exchange` row 20) has no reply note.
- When the bot answers with `message_agent` (a reply call, which is how bots usually answer), the call is a "Message to <sender>" tool row inside the exchange's expanded work (see Outgoing messages). A later message from the same bot, such as its answer to that reply, is the next exchange row, so a conversation between two bots reads Message from, Message from, one collapsed row each, and folds into a group (seen on the real server between two bots, recorded in `Tests/fixtures/scenarios/bot-thread`).
- While the exchange or its follow-up runs, the title pulses; like the live work log it stays collapsed until tapped, and the reply streams into the row's last note. The composer shows the running state, and a message the user sends while the last turn is an agent message or a delivery follow-up (`agentMessage` or `delivery` set) is queued until the turn ends, never steered into a reply addressed to another bot.
- Several exchanges are several rows, in order, between the user's own turns.
- A chat whose bot the roster reports working or waiting while the chat has no turn of its own shows the live "Working" row at the end of the transcript (no Stop: Desktop offers none for another process's turn, and the composer stays as for an idle chat). A send then waits as a queued bubble and goes out when the roster goes idle, like a queued send during the user's own turn. If the gateway still refuses the send (4090 / `SESSION_OWNER_BUSY`, a race with the roster), it becomes a queued bubble again, not a failure, and is retried at the next roster change. The roster covering the chat's own turn never shows the row, including the moments after that turn ends.
- An open chat catches up by itself. The exchange runs in a separate `hermes chat` process, so the chat that is already open (on screen, or kept from earlier in the session) gets no live events for it; it refetches its history when the bot row's position (`resolved_id` + `message_count`) moves while it is idle, so the new row appears within one roster refresh (about 2 s), like a new message in Messages, and the row preview read from that chat moves with it. A refetch keeps any local failure on the user's own turns. When the chat's own turn ends, it refetches once if the position moved meanwhile, so a reply that lands in the same moment still shows. Known gap: a chat that catches up this way only sees finished rows, so its exchange row does not pulse and a failure Hermes never wrote does not show.

## Sender's chat (the bot whose user asked for the message)

- The user's prompt and the bot's "queued" line, then one relay line ("@test-bot replied: …"). The relay is the bot's answer to the reply that arrives as `Message from <target>`: that turn shows as a plain reply (no bubble, no notice), and the delivery follow-up after it is hidden, because it only repeats the relay and can even be Hermes' `(empty)` sentinel (seen on the real server). When no reply message arrives (a failed delivery), the follow-up shows instead, so the failure is visible. The raw delivery notice never shows.
- Rule: each queued `message_agent` call (its result has a `process_id`) to @handle in a user-started turn consumes the next `Message from …(@handle)` turn as its reply (shown as the relay line); any other `Message from` turn, such as a second unprompted one, is an exchange and shows as a collapsed row. A delivery follow-up is hidden when its process completed normally (exit code 0, read from the notice) and a reply from its handle arrived after its origin that no other follow-up claimed yet. Pairing on the reply's position means an earlier mention whose delivery process died (no reply and no follow-up, seen on the real server) cannot strand a later follow-up as a duplicate relay. A follow-up from a process that exited non-zero always shows.
- A delivery that dies without a follow-up is Hermes losing it: no row says it failed. The sender's turn shows only the bot's queued line, and the target shows the exchange with no reply. Crew does not guess a timeout.
- The message itself shows as the "Message to <target>" tool row in the turn's work log, above the bot's queued line (see Outgoing messages).

## Outgoing messages (any chat whose bot sent one)

- Each `message_agent` call shows as a tool row in the work log of the turn that made it, in call order, instead of a "Message to" row after the turn: the target's 16 pt avatar in the icon slot (only when the handle is in the bot list, else the paperplane symbol), "Message to <target>" with the target's title from the bot list (the handle when it is not there, such as a deleted or relayed bot), the usual duration, status and chevron. The target is read like the mention peek reads it (`MessageAgentCall`: leading `@` and any `@host` suffix dropped, lowercased, `hermes` read as `default`). Expanded, it shows the message the bot sent as a quote, then the outcome line and the raw arguments and result like any tool row. A call in a running turn shows in the live work log with its spinner; live delivery status stays in the Waiting on teammates card.
- Expanded, it shows the message the bot sent as a quote, like the incoming row's first line. The `message_agent` tool row stays in the turn's own work log, with its arguments and result, as before.
- One rule for every turn kind: a user-started turn, a routine turn, an exchange (the target's reply call), a relay reply and a delivery follow-up that shows or folds into an exchange row. A hidden delivery follow-up (one that only repeats the relay) shows nothing, so a call made in it has no row.
- Pairing is unchanged. A call from a user-started or routine turn still consumes the target's next `Message from` turn as its reply (the relay line). A call from an exchange, a relay reply or a delivery follow-up does not, so a thread between two bots stays collapsed and out of the user's conversation instead of turning their back-and-forth into plain replies.
- A refused call (an error result, such as `runtime_coordination_required`, seen on the real server, or `runtime_offline`) or an unconfirmed one (`ambiguous`) puts the `delivery-failure.md` footnote under the turn that made the call, with the red tool row in its work log keeping the details: "Message to <Bot> failed." or "Not delivered." with the `runtime_offline` sentence in red, "Delivery to <Bot> couldn't be confirmed." in secondary text. A delivery that fails later: in the sender's chat its follow-up turn carries the footnote as before. When the follow-up folds into an exchange row (a target that answered with a reply call), the footnote shows under that exchange row, the turn whose call failed. The same holds for a relay reply's call: the follow-up stays hidden and the footnote shows under the relay reply. A turn with a footnote does not fold into a group.
- A call in a running turn has its tool row in the live work log, and the footnote waits for the turn to end.
- The row's id is the tool call's id plus `-to`, kept in the transcript's turn expansion set (expanding the `message_agent` tool row does not expand it), so a refetch keeps it expanded or collapsed.

## Bot list, push, other surfaces

- Preview: the last turn outside the collapsed rows, so a target whose latest activity is an exchange keeps reading its last user-facing line (nothing an exchange wrote). The sender reads the relay line. A `message_agent` call never sets the preview or time. Both on iPhone and Mac, from the open `ChatSession` (kept in step with the roster, see above) or from `BotStore`'s 20-row fetch. When neither has such a turn (the chat is still loading, the 20-row window is one long tool turn with no user row, or it holds only exchanges), the row shows the server's preview and `last_active`, never an empty line. That text is Hermes' own, so it is a fallback, not a guarantee of matching the chat.
- Time and unread: the time is the preview's (see Preview). Unread (`message_count`) ignores rows that only land inside collapsed rows: when the roster's position moves, the 20-row fetch counts the trailing rows after the last turn outside them (`Transcript.quietRows`) and the dot compares the position minus those rows with the read position, so an exchange alone never lights it. Until that fetch lands the new position is held back, so the dot and the local "Replied" alert do not flash. The count is stored with the cached chat; a failed fetch counts every row (the pre-change behaviour).
- Working: shown only for `working` and `waiting` from `session.active_list`. During an exchange the server reports the target `working` and it is; the collapsed row with its pulsing title is what the badge refers to. `starting` (an agent build after a resume, no turn) is not Working.
- Push: crew-push 0.3.2 sends no reply or failure push for an exchange turn or its delivery follow-up in the target; the sender's relay reply (its delivery turn) still pushes; approvals and questions always push. Known gap: an exchange's reply that asks the user something gets no push either, since crew-push cannot tell it from an answer to the other bot, and it no longer lights the unread dot or the preview. The local "Replied" alert (push off) follows the unread dot, so it stays quiet for exchange-only activity.
- Search: a hit inside an exchange (its incoming message, work or reply note) centres that row and expands it; a hit on a turn that made a `message_agent` call expands that turn's work log and centres the turn.
- Mention peek: unchanged; it reads the raw rows.
- Inspector: its conversation viewer renders the same visible transcript, so it shows the same tool rows; nothing else changes.

## States

- Empty chat with only exchanges: the rows are the transcript; no empty state.
- Long message or reply: the expanded rows wrap like work-log notes; the collapsed row is one line that wraps only at large Dynamic Type sizes. The same holds for a long outgoing message.
- Coalesced incoming message (seen on the real server, recorded in `bot-thread` row 1082): Hermes 0.23.0 joins a user row that got no answer with the next user row by a blank line and writes the result back onto the earlier row (`_merge_consecutive_users` in `agent/agent_runtime_helpers.py`, persisted through `_content_with_turn_override`). A delivery notice ends in Hermes' `[INTERNAL NOTIFICATION …]` line (`gateway/run_notifications.py`), so when the bot did not answer the notice, the next message lands after that line in the notice's row. Crew splits a merged row only where that line proves the join: at the blank line after it when text follows, and at the blank line before a delivery notice that ends in it when the row goes on past that notice to a last part that is not a notice (a prompt or `Message from` the bot did not answer, the notice, then the next message): the notice part stays the delivery follow-up (folded, hidden or shown as before, and the only part `DeliveryFailure` and the mention peek read), and each other part is read as its own row (only the first keeps the row's display kind), so an appended `Message from` is its own exchange row with its work and reply, an appended prompt of the user's is its own bubble, and a prompt or `Message from` before the notice keeps its own bubble or exchange row. Every pairing rule applies to the split rows in their order. A rest that itself holds such a delivery notice is split again. The split-off row's id is the row id plus `-1` (`-2` for the next), stable across refetches. Hermes keeps only the first part's time on the row, so a split-off row takes the time of the first non-user row after it and before the next user row (in the recording, Scout's 11-09 exchange no longer sits under 11-04), else the row's time. The split before a notice needs exactly one `[IMPORTANT: ` in the text before the footer, so a batch of process results Hermes folds into one row (`_fold_completion`, one header and one footer) stays whole. Merged rows with no footer (a prompt or `Message from` followed by another prompt or `Message from`) are not split (known gap: their tail reads as part of the first message): nothing ends that text, a user's own message can hold blank lines and quote a signature, and Crew does not guess. A prompt or `Message from` followed only by a notice is not split either (known gap: the notice reads as part of the message): the bot's answer belongs to the whole row and lands on its last part, which would then be the notice, often hidden, so the answer would vanish. Only history is split: an open chat sees an exchange by refetching it (see the Target's chat). The live text never carries a merge (read in the Hermes 0.23.0 source, not seen live): `begin(remote:)` reads `inflight.user`, set from the submitted text when the turn starts (`_start_inflight_turn`), and crew-push's `pre_llm_call` gets `original_user_message`; the merge happens later, on the model's message list. A window cut (below) can start at a merged row's split-off part: an appended prompt starts the window, and the row's parts before it are left out.
- Question for the user inside an exchange (recorded in `bot-thread` row 1081): the exchange's last note in the collapsed row (see the Target's chat), like an answer to the other bot.
- Refused or unconfirmed outgoing message: the row with its footnote, as in Outgoing messages.
- Failed or interrupted exchange: the row keeps its title; the failure shows under the turn as for any turn.
- Offline: rows render from the loaded transcript; nothing new.
- Window cut (the 20-row preview fetch or a cached 100-row page starts mid-exchange): the window starts at its first user row part that starts a turn (a prompt or a routine notice, also one split off a merged row), so a `Message from` reply or delivery follow-up whose origin was cut off is left out (`Transcript(window:)`, spec `docs/flows/instant-open.md`); a window with no such row starts at its first user row, where a delivery follow-up without its origin is hidden unless a user-started turn is loaded, as before; the preview then falls back to the last visible turn. Only the first rows of a 20-row window can be such an orphan, so a newer exchange in the window still sets the preview.
- Light and dark: system secondary styles only, both directions.
- iPhone and Mac: the same rows; nothing platform specific.
