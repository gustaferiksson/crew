# Bot-to-bot messages

A bot (the sender) calls `message_agent`; the other bot (the target) answers in its own Bot Chat; a delivery process carries the reply back to the sender. Hermes stores each step as ordinary rows, so Crew reads the shape from the rows (`Transcript.visible`).

Both directions show the same way: a message another bot sent this bot is a collapsed "Message from <sender>" row, a message this bot sent another bot is a collapsed "Message to <target>" row. Like a Mail thread, the target's chat shows both what came in and what went out. In the sender's chat a paired answer stays a relay line, so a back-and-forth there reads Message to, relay, Message to (recorded in `bot-thread`, the routine turn in Scout's chat).

## Target's chat (the bot that was messaged)

- Each exchange started by another bot is one collapsed row in the work-log style: the sender's 16 pt avatar (only when the handle is in the bot list; a relayed or deleted bot shows just the name), "Message from <sender>" with the name from the message itself, a chevron. Like Messages' grouped system rows, it says something happened without competing with the user's own conversation. It is a plain button labelled by its text, like the work-log header, so VoiceOver, Dynamic Type (it wraps) and the Mac keyboard behave the same.
- Expanded, it lists the incoming message, the bot's thinking and tool rows (the `message_agent` reply call included), and the bot's reply, all as secondary work-log note and tool rows, the incoming message first as a quote. The later delivery follow-up turn (the `[IMPORTANT: Background process …` row and the bot's acknowledgement) folds into the same row, so one exchange is one row. It lands seconds after the exchange; if the user has written in between, the follow-up still folds into the row above, which is the honest place for it.
- When the bot answers with `message_agent` (a reply call, which is how bots usually answer), a "Message to <sender>" row follows the exchange row (see Outgoing messages), so the chat shows that it wrote back. A later message from the same bot, such as its answer to that reply, is the next exchange row, so a conversation between two bots reads Message from, Message to, Message from, each one collapsed row (seen on the real server between two bots, recorded in `Tests/fixtures/scenarios/bot-thread`).
- While the exchange or its follow-up runs, the title pulses; like the live work log it stays collapsed until tapped. The composer shows the running state, and a message the user sends while the last turn is an agent message or a delivery follow-up (`agentMessage` or `delivery` set) is queued until the turn ends, never steered into a reply addressed to another bot.
- Several exchanges are several rows, in order, between the user's own turns.
- An open chat catches up by itself. The exchange runs in a separate `hermes chat` process, so the chat that is already open (on screen, or kept from earlier in the session) gets no live events for it; it refetches its history when the bot row's position (`resolved_id` + `message_count`) moves while it is idle, so the new row appears within one roster refresh (about 2 s), like a new message in Messages, and the row preview read from that chat moves with it. A refetch keeps any local failure on the user's own turns. When the chat's own turn ends, it refetches once if the position moved meanwhile, so a reply that lands in the same moment still shows. Known gap: a chat that catches up this way only sees finished rows, so its exchange row does not pulse and a failure Hermes never wrote does not show.

## Sender's chat (the bot whose user asked for the message)

- The user's prompt and the bot's "queued" line, then one relay line ("@test-bot replied: …"). The relay is the bot's answer to the reply that arrives as `Message from <target>`: that turn shows as a plain reply (no bubble, no notice), and the delivery follow-up after it is hidden, because it only repeats the relay and can even be Hermes' `(empty)` sentinel (seen on the real server). When no reply message arrives (a failed delivery), the follow-up shows instead, so the failure is visible. The raw delivery notice never shows.
- Rule: each queued `message_agent` call (its result has a `process_id`) to @handle in a user-started turn consumes the next `Message from …(@handle)` turn as its reply (shown as the relay line); any other `Message from` turn, such as a second unprompted one, is an exchange and shows as a collapsed row. A delivery follow-up is hidden when its process completed normally (exit code 0, read from the notice) and a reply from its handle arrived after its origin that no other follow-up claimed yet. Pairing on the reply's position means an earlier mention whose delivery process died (no reply and no follow-up, seen on the real server) cannot strand a later follow-up as a duplicate relay. A follow-up from a process that exited non-zero always shows.
- A delivery that dies without a follow-up is Hermes losing it: no row says it failed. The sender's turn shows only the bot's queued line, and the target shows the exchange with no reply. Crew does not guess a timeout.
- The message itself shows as a "Message to <target>" row between the bot's queued line and the relay (see Outgoing messages).

## Outgoing messages (any chat whose bot sent one)

- Each `message_agent` call that has a result shows as its own collapsed row right after the turn that made it, mirroring the incoming row: the target's 16 pt avatar (only when the handle is in the bot list), "Message to <target>" with the target's title from the bot list (the handle when it is not there, such as a deleted or relayed bot), a chevron. The target is read like the mention peek reads it (`MessageAgentCall`: leading `@` and any `@host` suffix dropped, lowercased, `hermes` read as `default`). Same work-log header style, plain button labelled by its text, Expanded/Collapsed value, wraps at large Dynamic Type sizes. It never pulses and has no Stop button: nothing is in flight for it.
- Expanded, it shows the message the bot sent as a quote, like the incoming row's first line. The `message_agent` tool row stays in the turn's own work log, with its arguments and result, as before.
- One rule for every turn kind: a user-started turn (bubble, work log, queued line, Message to, then the relay), a routine turn, an exchange (the target's reply call), a relay reply (a bot writing back again) and a delivery follow-up. Several calls in one turn are several rows, in call order. A call in a delivery follow-up gets its row where the follow-up's raw turn sits in time order, whether the follow-up shows on its own, is hidden or folds into an earlier exchange row; a folded one's row can therefore sit below the user's later turns, which is when the message went out.
- Pairing is unchanged. A call from a user-started or routine turn still consumes the target's next `Message from` turn as its reply (the relay line). A call from an exchange, a relay reply or a delivery follow-up does not, so a thread between two bots stays collapsed and out of the user's conversation instead of turning their back-and-forth into plain replies.
- A refused call (an error result, such as `runtime_coordination_required`, seen on the real server, or `runtime_offline`) or an unconfirmed one (`ambiguous`) still gets its row, like Messages keeps a message that was not delivered in the thread, with the `delivery-failure.md` footnote under it: "Message to <Bot> failed." or "Not delivered." with the `runtime_offline` sentence in red, "Delivery to <Bot> couldn't be confirmed." in secondary text. The red tool row in the work log keeps the details. A delivery that fails later keeps its row without a footnote: the sender's follow-up turn carries the footnote as before, and in the target's chat it stays under the exchange row the follow-up folds into.
- A call in a running turn has no row yet: the live work log shows it, and the turn stays the chat's last row. The row appears below the turn when the turn ends. A Message to row never counts as the chat's last turn for the running state, Stop or read-aloud, so a live delivery follow-up folding into an exchange row above its Message to row still shows the chat as running.
- The row's id is the tool call's id plus `-to`, kept in the transcript's turn expansion set (expanding the `message_agent` tool row does not expand it), so a refetch keeps it expanded or collapsed.

## Bot list, push, other surfaces

- Preview: the last visible turn, so a target whose latest activity is an exchange reads "Message from Crew Test", matching its time label. The sender reads the relay line, or "Message from <target>" when the target also sent something of its own afterwards. A "Message to" row never sets the preview or time: the turn right above it does (the bot's queued line, or "Message from <sender>" when it was a reply call), since the call happened before that turn's last line and the time label would move back. Both on iPhone and Mac, from the open `ChatSession` (kept in step with the roster, see above) or from `BotStore`'s 20-row fetch. When neither has a visible turn (the chat is still loading, or the 20-row window is one long tool turn with no user row), the row shows the server's preview, never an empty line. That text is Hermes' own (the last message, which can be a follow-up acknowledgement the chat folds away), so it is a fallback, not a guarantee of matching the chat.
- Time and unread: unchanged (`last_active`, `message_count`); now they always point at something visible.
- Working: shown only for `working` and `waiting` from `session.active_list`. During an exchange the server reports the target `working` and it is; the collapsed row with its pulsing title is what the badge refers to. `starting` (an agent build after a resume, no turn) is not Working.
- Push: crew-push 0.3.2 sends no reply or failure push for an exchange turn or its delivery follow-up in the target; the sender's relay reply (its delivery turn) still pushes; approvals and questions always push. The local "Replied" alert (push off) still fires on the unread edge, as before; it now matches a visible row, and muting it would need the preview fetch before the alert, so it stays a known gap.
- Search: a hit on the outgoing text centres the Message to row, whose quote holds the words (`turn(matching:)` reads the visible turns newest first); a hit elsewhere in the sending turn centres that turn as before.
- Mention peek: unchanged; it reads the raw rows, never the "Message to" rows.
- Inspector: its conversation viewer renders the same visible transcript, so it shows the same Message to rows; nothing else changes.

## States

- Empty chat with only exchanges: the rows are the transcript; no empty state.
- Long message or reply: the expanded rows wrap like work-log notes; the collapsed row is one line that wraps only at large Dynamic Type sizes. The same holds for a long outgoing message.
- Coalesced incoming message (known gap, seen on the real server, recorded in `bot-thread` row 1082): Hermes appended the next `Message from` to a delivery notice row, after its `[INTERNAL NOTIFICATION …]` line. Crew does not read that trailing message yet, so the new exchange's work and reply fold into the earlier exchange row the notice belongs to. Splitting the row is a follow-up.
- Refused or unconfirmed outgoing message: the row with its footnote, as in Outgoing messages.
- Failed or interrupted exchange: the row keeps its title; the failure shows under the turn as for any turn.
- Offline: rows render from the loaded transcript; nothing new.
- Window cut (the 20-row preview fetch or a cached 100-row page starts mid-exchange): the window starts at its first user row that starts a turn (a prompt or a routine notice), so a `Message from` reply or delivery follow-up whose origin was cut off is left out (`Transcript(window:)`, spec `docs/flows/instant-open.md`); a window with no such row starts at its first user row, where a delivery follow-up without its origin is hidden unless a user-started turn is loaded, as before; the preview then falls back to the last visible turn. Only the first rows of a 20-row window can be such an orphan, so a newer exchange in the window still sets the preview.
- Light and dark: system secondary styles only, both directions.
- iPhone and Mac: the same rows; nothing platform specific.
